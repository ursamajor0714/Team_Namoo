 1. 뉴스 분류 캐싱 없음 / 정당 페이지 응답 지연                    [P0 - 최우선]
================================================================================
 오늘 FastAPI(classification-api) 로컬 기동하고 실사용해보다가 심각한 수준이라
 최우선으로 올림. 정당 페이지가 "그냥 표시"가 아니라 매번 무거운 라이브 파이프라인을
 도는 구조라, 로딩이 수십 초 이상 걸리고 응답이 끊기는(Broken pipe) 경우까지 발생함.

 [현상 - 백엔드 로그 근거]
 - 같은 기사 URL(예: biz.chosun.com/...)을 10:08, 10:15, 10:22, 10:23에 반복
   크롤링·재분류함 - 정당 페이지를 다시 열 때마다 캐시 없이 매번 처음부터 다시 함
 - 10:15:29 로그: "Ignoring exception, response committed already: IOException:
   Broken pipe" - 응답이 너무 오래 걸려 브라우저가 먼저 연결을 끊은 것으로 추정.
   프론트에는 "불러오는 중..."만 계속 떠 있고 별도 안내 없음
 - 본문 크롤링 자체도 느림: 사이트별 최대 8초 타임아웃, JS 렌더링 페이지는 실패까지
   확인한 뒤에야 다음으로 넘어감 (15번 항목과 연결)

 [근본 원인]
 - NewsController.byLeaning()(/api/news/by-leaning), classify()(/api/news/classify)
   둘 다 매 요청마다 그 자리에서 collectionService.collect()(실시간 크롤링) +
   classificationModelClient.classify()(FastAPI 호출)를 처음부터 다시 수행함
 - classification 패키지 안에 NewsClassification(엔티티) + NewsClassificationRepository
   (JPA)가 있어서 분류 결과를 DB에 저장하는 코드 자체는 이미 존재하지만, 이건
   NewsClassificationService.classifyAndSave() 라는 별도 테스트 파이프라인 전용이고
   (클로드로 중복그룹핑 -> FastAPI 분류 -> DB 저장 -> 클로드로 한줄설명), 클래스 주석에도
   "확인 끝나면 이 패키지 전체를 삭제할 예정"이라 돼 있음. 아무 컨트롤러에서도 안 부르는
   죽은 코드 - 저장 로직은 있는데 실제 서비스 경로엔 전혀 안 쓰임

 [조치]
 - originalLink 기준으로 분류 결과를 DB에 캐싱(기존 NewsClassification 재활용 또는
   신규 테이블)해서, 이미 분류한 기사는 FastAPI/크롤링을 다시 안 하고 DB 값을 재사용
 - 기존 NewsClassificationService/Repository/Entity를 캐싱용으로 재활용할지, 삭제하고
   새로 만들지 결정 필요 (지금 이름/주석이 "테스트 전용, 삭제 예정"이라 그대로 쓰면 헷갈림)
 - 캐싱되면 (a) 재방문 시 즉시 응답 (b) FastAPI가 잠깐 꺼져 있어도 이미 분류된 기사는
   정상 노출 가능

================================================================================
 [현상]

   그대로 실행하면 로그인 자체가 안 될 가능성이 높음

 [조치]
 - server 브랜치에 위 @CrossOrigin 어노테이션 반영 (또는 검토 후 다시 작성)
 - 프론트 워킹트리 diff: MemberController.java 클래스 선언부에 어노테이션 한 줄 추가된

 4. 회원가입 검증 부재                                            [P0]
================================================================================
 서버는 사실상 아무 검증도 하지 않는다. 프론트 검증은 우회 가능하므로 서버가 최종 방어선.

 [현상 - 실제 요청으로 확인됨]
 - 아이디/비밀번호/닉네임 길이 제한 전무 - 1자도 통과, 빈 문자열도 통과
 - 비밀번호 복잡도 없음, 이메일 형식 검사 없음
 - 중복 검사는 loginId/email 만 (닉네임 없음)
 - 필수 필드 누락 시 DataIntegrityViolationException -> 500 + 스택트레이스 (400 아님)

 [조치]
 build.gradle: implementation 'org.springframework.boot:spring-boot-starter-validation'

 SignupRequest (프론트 규칙과 동기화):
   @NotBlank @Pattern(regexp = "^[A-Za-z0-9]{4,20}$")           loginId
   @NotBlank @Pattern(regexp = "^(?=.*[a-z])(?=.*[A-Z])(?=.*\\d)(?=.*[^A-Za-z0-9]).{8,}$") password
   @NotBlank @Email @Size(max = 100)                             email
   @NotBlank @Size(min = 2, max = 12)                             nickname

 - LoginRequest: @NotBlank loginId / password
 - 컨트롤러: signup(@Valid @RequestBody SignupRequest request)
 - GlobalExceptionHandler 에 @ExceptionHandler(MethodArgumentNotValidException.class)
   추가 -> 400 + 필드별 메시지 맵 (프론트는 필드 아래에 그대로 표시함)
 - 닉네임 비속어 필터는 프론트에만 있음 - 서버에도 둘지 정책 결정

 [참고 - 프론트 현재 검증 규칙]
   아이디  ^[A-Za-z0-9]{4,20}$
   비밀번호 ^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[^A-Za-z0-9]).{8,}$
   닉네임  2~12자 + 금지어 목록(src/constants/bannedWords.js)
   이메일  ^[^\s@]+@[^\s@]+\.[^\s@]+$

   parties            id PK / name unique / is_active (기타정당은 false로 보류)
   member_addresses   id PK / member_id FK / zipcode / address_base / address_detail
   members 신규 컬럼   supported_party_id FK NOT NULL / is_plus_member BOOLEAN /
                       custom_party_name NULL / email_verified BOOLEAN /
                       signup_channel VARCHAR NULL / agree_marketing BOOLEAN /
                       terms_agreed_at TIMESTAMP
 - SignupRequest: zipcode/addressBase/addressDetail/supportedParty/signupChannel/

 11. 이메일 인증 연동                                             [P1]
================================================================================
 프론트 "인증" 버튼은 현재 비활성. 코드 발송/검증 흐름 전체가 백엔드 몫.

 [흐름]
   1. POST /api/members/email/send-code  { email }  -> 6자리 코드, TTL 5분, 메일 발송
   2. POST /api/members/email/verify     { email, code } -> 200 (검증 토큰/세션 기록)
   3. 가입 시 이메일 검증 여부 확인

 [구현]
 - build.gradle: spring-boot-starter-mail
 - 개발: Gmail SMTP / 운영: AWS SES, 네이버클라우드, SendGrid 중 택1
 - application-local.properties 에 spring.mail.* (git 미추적)
 - 코드 저장: Redis 권장(SETEX TTL), 어려우면 email_verifications 테이블
 - 재발송 rate limit(예: 60초), 시도 횟수 제한

 12. 기존 버그 (500 / 406)                                       [P1]
================================================================================
 - 필수 필드 누락 -> 500(스택트레이스 노출). 4번(Bean Validation) 도입 시 자동 해결.
   그 전 임시 조치: GlobalExceptionHandler 에 DataIntegrityViolationException -> 400
 - 406 Not Acceptable: 순수 curl 등 Accept: */* 단독 요청에서만 발생, axios는 무관해서
   실제 앱엔 영향 적음(우선순위 낮음). String 대신 JSON 객체 반환으로 정리하면 해소
 - GlobalExceptionHandler 가 member 패키지 안에 있음 -> 공통 위치로 이동 검토

 15. 본문 추출 최후 폴백 품질                                     [P1]
================================================================================
 오늘 "통일교 한학자, 1심 총 징역 2년…" 기사에서 실제로 확인한 문제.

 [현상]
 - ArticleTextExtractor.extract() 추출 순서: readability4j -> BODY_SELECTORS ->
   링크밀도 휴리스틱 -> 최후 폴백 doc.body().text()(길이 체크 없이 그대로 반환)
 - 위 기사는 news1.kr 페이지로 본문이 JS로 늦게 렌더져서, Jsoup이 받아온 정적 HTML엔
   실제 기사 내용이 없는데도 최후 폴백이 페이지 뼈대 텍스트(150자)를 "본문"으로 반환
 - 실제 반환값: 제목 반복 + 업데이트 시각 + "구글에서 뉴스1 즐겨찾기"(중복) +
   관련기사 제목 + "관련 키워드..." - 진짜 기사 내용은 0글자
 - content.isBlank() 체크는 "완전히 빈 경우"만 걸러내서 이런 "비었진 않지만 가짜인"
   경우를 못 걸러냄

 [조치]
 - 최후 폴백에도 MIN_CANDIDATE_LENGTH 같은 최소 길이 체크 적용, 짧으면 예외 던져 제외
 - "구글에서 즐겨찾기", "관련 키워드" 등 UI 문구 패턴도 노이즈로 추가 검토

 참고 - 현재 auth API 계약 (변경 아님, 확장 대상)
================================================================================
 프론트가 이미 이 계약에 맞춰 연동돼 있음. 그대로 유지하고 위 항목들로 확장할 것.

   POST /api/members/signup   { loginId, password, email, nickname } -> 200
   POST /api/members/login    { loginId, password } -> 200 + Set-Cookie: JSESSIONID
   GET  /api/members/me       -> 200 { id, loginId, email, nickname } | 401
   POST /api/members/logout   -> 200

 - 세션 쿠키 방식(JSESSIONID, 브라우저 종료 시 만료). CORS는 2번 항목 참고
 - 실패 시 400 + 한글 메시지 문자열
 - "로그인 유지" 체크박스는 프론트에 UI만 있음 - 실제로 유지하려면
   server.servlet.session.timeout 연장 또는 remember-me 토큰 + 영속 쿠키 필요
