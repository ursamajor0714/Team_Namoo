## 무엇을 했나

`origin/server` 의 오늘자 커밋 3건까지 받아서, **프론트(front 브랜치 코드) ↔ 백엔드(server 브랜치 코드)**
를 로컬에서 실제로 붙여 보고 오늘 추가된 API 를 전부 호출해 확인했다.
사용자가 3일째 띄워 둔 docker 스택(8080/5173)은 건드리지 않았고, 별도 포트로 병행 기동했다.

| 구성 | 주소 | 비고 |
|---|---|---|
| 백엔드 (server 브랜치) | `http://localhost:8081` | git worktree + `SPRING_PROFILES_ACTIVE=docker`, H2 인메모리 |
| 프론트 (Vite) | `http://localhost:5174` | `VITE_API_BASE_URL=http://localhost:8081` |
| 기존 docker 스택 | 8080 / 5173 | 그대로 유지 (front 브랜치 코드) |

CORS 는 `APP_CORS_ALLOWED_ORIGINS` 로 5174 를 추가했다. preflight 200,
`Access-Control-Allow-Credentials: true`, 로그인 시 `JSESSIONID` 발급까지 확인.

## 안 되는 것 / 남은 것

### 1. 프론트가 아직 아무것도 안 붙어 있다 (가장 큰 덩어리)

프론트가 실제로 호출하는 API 는 **인증·이메일·뉴스뿐**이다. 전수 조사 결과:

```
/api/members/{signup,login,logout,me,check-id,check-email}
/api/email/{send-code,verify-code}
```

즉 오늘 서버에 들어온 것(게시판·글·댓글·추천·신고·공지·광고·관리자 콘솔 전체)은
**프론트에서 호출하는 코드가 한 줄도 없다.** 아래 파일이 여전히 더미/localStorage 로 동작한다.

- `components/AdManage.jsx`, `components/AdRail.jsx`, `store/adStore.js` — 광고, localStorage
- `components/PostManage.jsx` — 관리자 게시글 관리, 더미
- `pages/BoardPage.jsx`, `pages/PostDetailPage.jsx` — 게시판/상세, 더미 15건
- `api/` 디렉토리에 `authApi.js`, `newsApi.js` 만 있음 — boardApi/adminApi/adApi 가 없음

**→ 다음 프론트 작업 = 이 API 클라이언트들을 새로 만들고 목을 걷어내는 것.**

### 2. 백엔드에 아직 없는 것

| 항목 | 출처 | 상태 |
|---|---|---|
| 회원 DB 영속성 | `BACKEND_TODO 3번` | **미해결.** `jdbc:h2:mem:...` 그대로 — 서버 재시작하면 회원 전부 소멸 |
| 회원용 게시글 검색 API | `BACKEND_TODO 13번` | **없음.** 관리자용 기사 검색만 있고 게시글 검색은 회원/관리자 모두 없음 |

| 결제/구독 테이블 | `ADMIN 1-4` | 없음 → `weeklyRevenue` 항상 `0` |

### 3. 검증 못 한 것 (환경 때문)

- **S3 presign 실제 왕복** — 로컬에 AWS 자격증명이 없어 `AWS_S3_BUCKET 환경변수가 설정되지 않았습니다`
  로 500. 커밋 메시지에도 미검증으로 적혀 있음. EC2 인스턴스 롤 붙인 뒤 확인 필요.
- **이메일 실발송 → 가입 완료** — 로컬에 Gmail SMTP 자격증명이 없어 가입이 `이메일 인증을 완료해주세요.`
  에서 막힌다. 코드상 `@Transactional` 수정은 들어가 있으나 실제 흐름은 여전히 미검증.

### 4. 이번에 새로 발견한 문제

- **에러 응답에 스택트레이스가 그대로 나간다.** 잘못된 요청 하나로
  `trace: "org.springframework... at java.base/java.lang.Thread.run"` 전체가 응답 body 에 실려 온다.
  `ADMIN 5-2` 의 "응답에 민감정보가 안 새는지" 항목에 해당. 운영 배포 전 반드시 막아야 함.
- **회원가입에서 `agreeMarketing` 을 null 로 보내면 400 + JSON parse error** 가 그대로 노출된다
  (`Cannot map null into type boolean`). 프론트가 체크박스 초기값을 null 로 두면 바로 터진다.
  `boolean` → `Boolean` 으로 바꾸거나 기본값 처리 필요. `BACKEND_TODO 12번`(500/406 이월 버그) 계열.
- **presign 은 크기 검증보다 버킷 설정 검사가 먼저다.** 그래서 2MB 초과 요청도 "용량 초과 400" 이 아니라
  "버킷 미설정 500" 이 난다. 로컬에서는 크기 제한 자체를 확인할 수 없다. 순서를 바꾸는 게 맞다.
- **정지(SUSPENDED) 회원의 글쓰기 차단은 로그인 시점에만 검사한다.** 이미 세션을 들고 있는 회원은
  정지 후에도 세션이 만료될 때까지 글을 쓸 수 있다. `ADMIN 3-3` 의 의도와 어긋남.

## 정리

서버는 TODO 문서 기준 **1~5순위를 사실상 다 끝냈다.** 남은 백엔드 일은 6순위(매출/감사로그/광고 집계)와
DB 영속성·게시글 검색 정도다. **지금 병목은 프론트다** — 서버 API 는 다 있는데 화면이 전부 목이다.

# 추가 · 백엔드 문제 4건 (팀원 전달용, 쉬운 설명)

담당 확인 결과 **백엔드는 팀원 소관**이므로 이쪽에서 고치지 않는다. 아래는 그대로 전달하면 되는 내용.
넷 다 백엔드에서만 고칠 수 있고, 프론트가 할 일은 없다.

## 1. 에러 응답에 스택트레이스가 그대로 나간다

잘못된 요청 하나에 서버 내부 구조도(`org.springframework... AdminAdService.java:77 ... Thread.run`)가
응답 body 에 통째로 실려 나온다. 원래 서버 로그에만 남아야 할 개발자용 기록이다.
공격자에게 "이 서버는 스프링이고 이런 클래스가 있고 여기서 터진다"를 알려주는 셈이라
**운영 배포 전에 반드시 막아야 한다.** `server.error.include-stacktrace=never` 로 해결되고,
사용자에게는 `{"message": "..."}` 만 내려주면 된다.

## 2. 회원가입에서 체크박스 하나 때문에 터진다

`agreeMarketing` 이 `boolean`(참/거짓만 허용) 으로 선언돼 있어서, 프론트가 값을 비워서(null)
보내면 `Cannot map null into type boolean` 이라는 영어 파싱 에러가 400 과 함께 그대로 노출된다.
사용자는 뭘 잘못했는지 알 수 없다. `boolean` → `Boolean` 으로 바꾸고 "비어 있으면 false" 처리하면 끝.

## 3. 광고 이미지 용량 제한을 확인할 방법이 없다

presign 이 **버킷 설정 검사 → 파일 크기 검사** 순서라, 버킷이 없으면 크기 검사에 도달하지 못한다.
그래서 3MB 파일을 올려도 "용량 초과 400" 이 아니라 "버킷 미설정 500" 이 난다.
S3 를 붙이면 증상이 안 보이게 되므로 **지금 순서를 뒤집어(파일 검증 먼저) 놓는 게 맞다.**

## 4. 정지시켜도 이미 로그인해 있으면 계속 글을 쓴다

회원 상태(`getStatus()`)를 보는 곳이 `MemberService.login()` **한 군데뿐**이다. 전수 확인함.
따라서 정지 처리해도 그 회원은 로그아웃 전까지 글·댓글·추천을 계속 쓸 수 있고,
다음 로그인 시도에서야 막힌다. 관리자 콘솔 TODO 의 "정지 → 글쓰기 차단" 의도와 어긋난다.
**글쓰기·댓글·추천·신고 시점에도 상태를 한 번 더 검사**해야 한다.
(프론트에서 버튼을 숨기는 건 눈속임이라 소용없다 — TODO 문서에도 같은 말이 적혀 있다.)

# 추가 · 광고 S3 연동 지시 검토 (팀원 메시지)

팀원에게서 "EC2 에 S3 환경변수 4줄 추가 + 프론트에서 presign 업로드로 교체" 지시가 왔다.
그대로 실행하기 전에 배포 상태를 확인했고, **순서가 어긋나 있다는 것을 발견했다.**

## 결론 — env 만 넣으면 아무 일도 일어나지 않는다

**배포된 백엔드에는 광고 API 자체가 없다.** 그러므로 `AWS_S3_BUCKET` 을 넣고 재시작해도
`/api/admin/ads/image/presign` 은 500 이 아니라 **404** 가 난다.

| 브랜치 | 최신 커밋 | 날짜 | 광고 API |
|---|---|---|---|
| `origin/main` (= 배포 기준) | `bff5e0e 새로운시작` | 2026-09-03 | **없음** (`ad/` 패키지 0개) |
| `origin/server` (팀원 작업) | `d2b42a4 SNS 로그인…` | 2026-09-07 | 있음 (`89bed51`) |

`origin/main` 은 9/3 이후 멈춰 있고, `server` 가 **6 커밋 앞서 있다**
(관리자 콘솔, 기사 visibility, 게시판/댓글, **광고+S3 presign**, 추천/신고/공지, SNS 로그인).
Amplify 는 `main` 을 보고 있고 EC2 의 `app.jar` 도 `main` 에서 빌드한 것이다.

### 올바른 순서

1. `server` → `main` 병합 (또는 `server` 에서 빌드)
2. `./gradlew bootJar` → `scp` 로 EC2 의 `~/app/app.jar` 교체
3. `~/app/namoo-spring.env` 에 S3 환경변수 추가
4. `sudo systemctl restart namoo-spring`
5. 그 다음에야 프론트 연동이 의미가 있다

## 팀원 지시서에서 사실과 다른 부분

| 팀원이 적은 것 | 실제 (docs/AWS_DEPLOY_PROGRESS.txt 및 서버 확인) |
|---|---|
| 호스트 OS `Ubuntu` | **Amazon Linux 2023**. SSH 계정도 `ubuntu` 가 아니라 `ec2-user` |
| env 파일 `/etc/namoo-spring.env` | **`~/app/namoo-spring.env`** (= `/home/ec2-user/app/namoo-spring.env`) |
| `AWS_REGION` 없으면 생략 가능 | 맞음. `application.properties:22` 에 `${AWS_REGION:ap-northeast-2}` 기본값 있음 |
| 배포 브랜치 `server` | 배포 기준은 **`main`**. `server` 는 팀원 작업 브랜치일 뿐 배포되지 않는다 |

접속: `ssh -i ~/.ssh/team-namoo-model.pem ec2-user@15.165.118.162`

## 인스턴스 롤 vs 액세스 키

EC2 `namoo-spring` 에 인스턴스 롤이 붙어 있는지는 서버에서 확인해야 한다.

두는 것보다 안전하므로 그쪽을 우선한다.**

## 프론트 작업 계약 (서버 코드에서 직접 확인)

`AdminAdService` / `AdminAdController` / `AdController` 를 읽고 확정한 내용.

- `POST /api/admin/ads/image/presign` `{contentType, size}` → `{uploadUrl, imageUrl}`,
  **presigned URL 유효기간 5분**
- 허용 형식 **png / jpeg / webp 3종만** (SVG 는 XSS 때문에 400), **2MB 초과 400**
  → 프론트의 `MAX_IMAGE_BYTES = 1_500_000` (`AdManage.jsx:5`) 을 2MB 로 맞춰야 한다
- S3 PUT 시 `Content-Type` 헤더가 presign 요청의 `contentType` 과 **정확히 같아야** 서명이 맞는다
- `POST /api/admin/ads` 성공 **201**, `DELETE /api/admin/ads/{id}` 성공 **200** (204 아님)
- `GET /api/ads?page=&side=` 는 활성 광고 없으면 **204 + 빈 body**
  → axios 에서 `data` 가 빈 문자열로 오므로 `status === 204` 로 분기해야 한다
- `side` 는 요청·응답 모두 **대문자 `LEFT`/`RIGHT`**.
  프론트(`adStore.js`, `AdManage.jsx`, `AdRail.jsx`)는 전부 소문자 `'left'/'right'` 기준이라 변환 필요
- `startAt`/`endAt` 은 `LocalDateTime`. 서버가 `endAt > startAt` 을 **엄격히** 요구하므로
  (같으면 400) 프론트의 `>` 비교(`AdManage.jsx:49`)를 `>=` 로 바꿔야 한다

### 팀원 메시지에 없던 주의점 — 업로드는 돼도 이미지가 안 보일 수 있다

서버가 돌려주는 `imageUrl` 은 CloudFront 미설정 시
`https://teamnamoo-ad-assets.s3.ap-northeast-2.amazonaws.com/ads/<uuid>.png` 형태다.
이걸 `<img>` 로 띄우려면 버킷에 **공개 읽기(GetObject) 정책**이 있어야 한다.
팀원이 설정했다는 CORS 는 브라우저의 **업로드(PUT)** 를 위한 것이라 별개다.
공개 읽기가 없으면 업로드는 성공하는데 화면엔 깨진 이미지가 뜬다 — 팀원에게 확인 필요.

## 병합 확인 — 충돌 없음, fast-forward

`git merge-base --is-ancestor origin/main origin/server` = **참**. 즉 `main` 은 `server` 의 조상이고
`server` 에만 있는 커밋 6개를 얹으면 끝이다. **충돌 0건, fast-forward.**

- `server` 에 없는 `main` 커밋: **없음**
- `origin/front` 는 `origin/main` 과 **완전히 동일한 커밋**(`bff5e0e`) — 별도로 신경 쓸 것 없음
- 9/3 배포용 수정(`@Lob`, `CorsConfig` env 주입, 시크릿 환경변수화)은 **`server` 에도 그대로 살아 있다.**
  따라서 `server` 를 배포해도 MySQL CLOB 버그나 CORS 문제는 재발하지 않는다.

주의: `server` 브랜치에 **프론트 파일 변경도 섞여 있다** (`index.html`, `src/api/authApi.js`,
`src/pages/SignupPage.jsx` — SNS 로그인 관련). 프론트는 사용자 담당이므로 병합 후 이 3개 파일의
변경 내용을 확인할 것.

## 배포 브랜치 운영 문제 (팀원에게 되물을 것)

팀원은 `server` 에만 커밋하는데 **배포는 `main` 을 본다.** 9/3 이후 `main` 이 한 번도 갱신되지 않아
9/4~9/7 작업분 6커밋이 전부 배포 안 된 상태로 쌓였다. 지시서에도 "배포 브랜치: server" 라고 적혀 있어
팀원은 `server` 가 배포되는 줄 아는 것으로 보인다. **배포 기준 브랜치를 한 번 못박아야 한다.**

## 배포 절차 (사용자 확정, 2026-09-07)

위 "fast-forward 가능" 은 기술적 사실일 뿐이고, **실제 절차는 곧바로 병합하지 않는다.**

```
server (팀원 작업)  →  사용자가 로컬로 가져와 직접 테스트  →  통과한 것만 main  →  배포
```

`main` 은 검증된 것만 들어가는 브랜치이고 사용자의 로컬 테스트가 그 관문이다.
따라서 `server` → `main` 직접 병합은 하지 않는다.

## 키 확인 — 버킷은 팀원 계정에 있다

# 버그 · 회원가입에서 "존재하지 않는 정당입니다" (2026-09-07)

배포 후 사용자가 발견. 회원가입에서 지지 정당을 고르고 완료를 누르면 400 + "존재하지 않는 정당입니다."

## 원인 — 프로덕션 DB 의 parties 테이블이 비어 있었다

RDS 를 직접 조회한 결과 `parties` 0건, `members` 0건.

`MemberService.resolveParty()` 가 `partyRepository.findByName(name)` 로 찾다가 없으면 저 메시지를
던진다. 프론트가 보내는 이름(`constants/parties.js`)과 `data.sql` 의 이름은 **정확히 일치**하므로
오타 문제가 아니라 **시드 데이터가 아예 안 들어간 것**이었다.

### 왜 로컬에선 되고 배포에선 안 됐나

`spring.sql.init.mode` 의 기본값이 **`embedded`** 이기 때문이다. Spring Boot 는 H2 같은 내장 DB
에서만 `data.sql` 을 실행하고 **MySQL 같은 외부 DB 에서는 실행하지 않는다.**
`application.properties` 에는 `spring.jpa.defer-datasource-initialization=true` 만 있고
`spring.sql.init.mode` 지정이 없다. 그래서 로컬 H2 는 정당 6개가 들어가고 RDS 는 0건이 된다.
**배포 첫날(9/3)부터 계속 이 상태였다.**

## 조치 — RDS 에 정당 6건 직접 INSERT (완료)

`parties.name` 에 UNIQUE 제약이 이미 걸려 있어 `INSERT IGNORE` 로 안전하게 넣었다.
결과: id 1~6 (더불어민주당·국민의힘·조국혁신당·개혁신당·진보당 활성, 기타정당 비활성).

주의: **`spring.sql.init.mode=always` 만 켜서 해결하려 하면 안 된다.** `data.sql` 이 평범한
`INSERT` 라 두 번째 기동부터 UNIQUE 위반으로 기동 자체가 실패한다. 코드로 영구히 고치려면
`data.sql` 을 `INSERT IGNORE` 로 바꾼 뒤 `always` 를 켜야 한다. (미조치 — 담당 확인 필요)

## 부수 사항

- **프로덕션 회원 수 0명.** 배포 후 아무도 가입하지 못한 상태였다. 관리자 계정이 없는 이유도 이것.
  정당이 들어갔으니 이제 가입이 뚫린다. 가입한 계정의 `role` 을 올리면 관리자 콘솔 진입 가능.

  즉 정당 에러를 봤다는 건 이메일 인증까지는 통과했다는 뜻이다.

| 신고관리 | **없었음** | 상태·대상 필터, 처리/반려/되돌리기 |
| 관리자 판별 | `loginId === 'dbrmsgh11'` 하드코딩 | 서버 `role` (USER/ADMIN/SUPER_ADMIN) |

## 서버와 맞춘 지점 (틀리면 400 이 나는 것들)

- 광고 이미지: **PNG·JPG·WEBP만, 2MB 이하.** 프론트 상한이 1.5MB 였어서 올렸다.
  S3 PUT 의 `Content-Type` 은 presign 요청 때와 **정확히 같아야** 서명이 맞는다. presign 유효기간 5분.
- `side` 는 `LEFT`/`RIGHT` 대문자. 프론트는 전부 소문자였다.
- 광고 기간은 `endAt > startAt` **엄격**. 같으면 400 이라 프론트 검사도 `>=` 로 바꿨다.
- `GET /api/ads` 는 광고가 없으면 **204 + 빈 본문** → axios `data` 가 빈 문자열이라 `status` 로 분기.
- 회원 상태 검색은 서버가 enum 이름(`ACTIVE`)을 받는다. 한글로 쳐도 되게 프론트에서 변환한다.
- 목록 API 는 `Page` 라 `content` / `totalElements` 를 꺼내 써야 한다.

## 알면서 남겨둔 것

- **기사관리에서 뉴스 팝업을 못 띄운다.** `AdminArticleResponse` 에 본문(content/contentHtml/
  imageUrl/pubDate)이 없어서 `NewsModal` 을 채울 수 없다. 지금은 제목을 누르면 원문이 새 탭으로
  열린다. 팀원이 응답에 본문 필드를 추가해 주면 원복 가능하다.
- **금주 매출은 항상 0원.** 결제/구독 테이블이 없어 서버가 0 을 준다(`ADMIN 1-4`). 예전 프론트는
  Plus 회원 수 × 4900원으로 **지어내고 있었다.** 지어낸 값을 화면에 띄우는 것보다 0 이 정직하다.
- **목록 페이지 이동 UI 가 없다.** 한 번에 100건까지만 받는다. 회원이 100명을 넘으면 추가가 필요하다.
- **글쓴이 정지**는 게시글 API 가 닉네임만 주므로 닉네임으로 회원을 찾아 상태 API 를 호출한다.
  닉네임이 바뀌었거나 중복이면 못 찾을 수 있다.

## 광고 레일 노출 폭 (결론: 그대로 둔다)

사용자 맥북에서 광고가 안 보여 기준을 1480px → 1400px → 1280px 까지 낮췄다.
그런데 실제 창 폭을 재보니 **100% 배율에서 915px** 이었다(1144px 은 75% 배율 상태였다).
본문 `#root` 가 1126px 이라 915px 창에서는 본문조차 다 못 펴는 폭이고, 광고가 들어갈 여백은 0 이다.

여백이 광고 자리를 "먹고" 있는 게 아니라, **그 여백이 곧 광고 자리**다. 본문 안쪽 패딩은
좌우 20px(`.news-list`)뿐이라 줄일 것도 없다. 본문 폭 자체를 줄이면 자리가 생기지만 전 페이지
레이아웃이 바뀌므로 **하지 않기로 했다.** 넓은 화면에서는 정상 노출되는 것을 확인했다.

# 버그 · 관리자 콘솔의 모든 쓰기 동작이 "네트워크 에러" (2026-09-07)

프론트 연동 직후 광고 이미지 업로드에서 발견. 증상은 광고였지만 **관리자 콘솔의 쓰기 동작 전체**가
막혀 있었다.

## 원인 — 인증 검사기가 CORS 예비 요청까지 401 로 막았다

```
OPTIONS /api/admin/ads/image/presign   →   HTTP 401
```

브라우저는 다른 도메인으로 POST/PATCH 를 보내기 전에 **CORS 예비 요청(preflight, OPTIONS)** 을
먼저 보내 허락을 받는다. 이 예비 요청에는 **세션 쿠키가 실리지 않는다.**
그런데 `AdminAuthInterceptor` 가 `/api/admin/**` 전체를 검사하면서 이 OPTIONS 도
"로그인 안 됨"으로 보고 401 을 돌려주고 있었다. 브라우저는 예비 요청이 2xx 가 아니면 본 요청을
아예 보내지 않으므로, 프론트에는 응답 없이 axios 의 `Network Error` 만 남는다.

### 왜 조회는 되고 저장만 안 됐나

**단순 GET 은 예비 요청을 보내지 않는다.** 그래서 회원 목록·광고 목록·기사 목록은 정상으로 떴고,
등록·수정·삭제만 전부 실패했다. 증상이 "광고 업로드만 안 된다"처럼 보였지만 실제로는
회원 저장/정지/임명, 기사 감추기, 게시글 삭제·공지, 신고 처리까지 **전부** 막혀 있었다.

## 조치

`config/AdminAuthInterceptor.preHandle()` 맨 앞에 예비 요청 통과를 추가했다.

```java
if (CorsUtils.isPreFlightRequest(request)) {
    return true;
}
```

예비 요청은 실제 데이터를 주고받지 않고 "이 요청을 보내도 되나"만 묻는 것이라 통과시켜도
보안상 문제가 없다. 실제 요청은 그대로 인증을 거친다.

## 배포 후 검증

| 요청 | 결과 |
|---|---|
| `OPTIONS /api/admin/ads/image/presign` | **200** (전 401) |
| `OPTIONS /api/admin/ads` | 200 |
| `OPTIONS /api/admin/members/1/status` | 200 |
| `OPTIONS /api/admin/reports/1/status` | 200 |
| `POST /api/admin/ads/image/presign` 비로그인 | **401** (인증은 그대로 동작) |
| `GET /api/admin/members` 비로그인 | 401 |

EC2 배포 완료(기동 정상, 에러 로그 0건). 이전 jar 은 `~/app/app.jar.bak-preflight` 로 백업.

**팀원에게 알릴 것:** 이 수정은 `main` 에만 들어갔다. 팀원의 `server` 브랜치에는 아직 없으므로
다음에 `server` 를 가져올 때 되살아나지 않도록 동기화가 필요하다.
